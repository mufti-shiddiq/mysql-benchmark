# Benchmark Methodology

`mysql-benchmark` is designed for practical comparison, not official certification.

## What It Measures

The CLI measures elapsed time from the client process for each benchmark case. That means each timing includes:

- client-side query dispatch
- network transit
- MySQL parsing/planning/execution
- result transfer
- client-side result consumption

`SELECT 1 latency` is intentionally labeled as MySQL round-trip latency plus MySQL processing overhead. It is not pure TCP RTT.

## Warmup and Iterations

Each benchmark case runs warmup iterations before measured iterations.

Warmup results are discarded. Measured iterations are summarized with:

- min
- avg
- p50
- p95
- p99
- max

Percentiles use a deterministic nearest-rank calculation over sorted durations.

## Fair Comparisons

For provider comparisons, keep the client location fixed:

```text
Same VPS
  -> Provider A MySQL
  -> Provider B MySQL
```

Avoid comparing results from different client locations, such as a laptop for one database and a VPS for another.

## Important Variables

Results can change with:

- region and network distance
- MySQL version
- CPU, memory, and storage
- connection limits
- buffer pool and cache state
- indexes and query plans
- noisy neighbors on shared infrastructure
- concurrent production traffic

Run multiple benchmark passes before making purchasing or migration decisions.

## Dataset Notes

The current workloads use synthetic data generated by the CLI. This keeps the repository easy to distribute and avoids redistributing third-party benchmark datasets.

The TPC-H-inspired workload uses familiar table families and Q01-Q22 case names, but it is not an official TPC-H compliant benchmark.
